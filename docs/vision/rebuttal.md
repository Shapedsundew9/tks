## LD-10: Staging Approval Advisory Lock Hold Time & Pre-Lock Validation

* **Target:** `architecture.md` §5.2 (Concurrency Model), §9 (Decisions D-20, D-38, D-70)
* **Critique Summary:** The Lead Developer proposed separating transaction read-validation from topological write commit during staging approvals (`POST /api/v1/staging/approve`): executing Invariant INV-1 ancestor verification CTEs and draft summary aggregation under `READ COMMITTED` first *outside* the global transaction advisory lock, and acquiring `pg_advisory_xact_lock(hashtext('tks_structural_mutation'))` immediately prior to updating `lifecycle_state` on edges and nodes, in order to minimize lock hold time to $<5\text{ ms}$.
* **Disposition:** **Respectfully Rebutted** (Rejected as Decision D-70 in `architecture.md`)
* **First-Principles Architectural Rationale:**
  1. **Time-of-Check to Time-of-Use (TOCTOU) Race Condition:**
     Invariant INV-1 mandates that every active functional specification and implementation task must maintain an unbroken directed path terminating at an authorized active requirement node. If the ancestor verification CTE executes under `READ COMMITTED` prior to acquiring the global advisory lock, it evaluates against a point-in-time database snapshot. Before the staging approval transaction acquires the global advisory lock, an interleaving concurrent transaction (such as an administrative rollback `revert_mutations` or an automatic document revision supersession sweep per D-55/LD-6) can acquire the advisory lock, supersede or revert the parent requirement, and commit. When the staging transaction subsequently acquires the advisory lock and promotes child specifications or tasks to `ACTIVE`, it commits child entities whose parent requirement is already superseded or reverted. This creates dangling, invalid active specifications in direct violation of Invariant INV-1.
  2. **Advisory Lock Scope & Serialization Invariants:**
     In PostgreSQL, transaction-level advisory locks (`pg_advisory_xact_lock`) are released exclusively upon transaction commit or rollback. Acquiring the lock halfway through the transaction does not allow other transactions to interleave safely with the preceding reads; rather, it allows un-serialized topological state to influence the validation check. To mathematically guarantee that the graph topology verified by the INV-1 ancestor CTE remains invariant throughout the promotion commit, the validation CTE and the state promotion updates MUST execute within the exact same mutual exclusion critical section protected by the advisory lock.
  3. **Empirical Lock Hold Duration at Target Scale:**
     The critique hypothesizes that evaluating ancestor paths and aggregating draft summaries for a 60-node batch serializes all concurrent agent mutations across the system. However, on indexed PostgreSQL adjacency tables (`graph_edges` with B-tree indexes), a recursive CTE evaluating ancestor paths for 60 nodes executes in **1 to 3 milliseconds** on warm cache. Furthermore, draft summaries are aggregated from `graph_nodes.attributes->'draft_revisions'` already staged in the job. The total critical section duration under the advisory lock remains $<5\text{ to }10\text{ ms}$.
  4. **Operational Cadence vs. Structural Safety:**
     Staging approvals are human-in-the-loop operational actions executed infrequently (minutes, hours, or days apart), whereas autonomous agent mutations execute continuously. Concurrently, native row-level locking (`SELECT ... FOR UPDATE`) already handles concurrent leaf attribute edits and task status transitions independently of the advisory lock (Decision D-30). Sacrificing absolute topological correctness and opening a fatal TOCTOU corruption window to save 2–3 milliseconds on an infrequent human approval gate compromises system integrity for negligible operational gain.
* **Architectural Resolution:**
  Retain mandatory acquisition of `pg_advisory_xact_lock(hashtext('tks_structural_mutation'))` at the very beginning of the batch promotion transaction (`POST /api/v1/staging/approve`), preceding both Invariant INV-1 ancestor CTE verification and node/edge lifecycle promotions, in strict accordance with the lock acquisition hierarchy (Decision D-66). Staging summaries may be pre-calculated in memory before opening the database transaction, but all database reads and writes asserting topological invariants must remain strictly serialized within the advisory lock boundary.
